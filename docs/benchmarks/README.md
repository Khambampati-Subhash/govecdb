# Benchmarks

Every chart in this repository is generated from `results.csv`, and `results.csv`
is generated by the same tests that CI runs. There is no separate benchmarking
script whose numbers can drift away from the ones the test suite defends.

## Regenerating

```bash
go test ./internal/hnsw/ -run TestSweep -results docs/benchmarks/results.csv -timeout 40m
go run docs/benchmarks/plot.go
```

The first command takes a few minutes; the second is instant.

## How the two modes work

The sweeps in [`internal/hnsw/recall_test.go`](../../internal/hnsw/recall_test.go)
are one piece of code with two jobs, selected by the `-results` flag:

| | without `-results` | with `-results` |
|---|---|---|
| Grid | narrow (3–5 cells per sweep) | wide (6–8 cells per sweep) |
| Corpus | 800 vectors | 5,000 vectors |
| Queries | 50 | 200 |
| Runtime | ~20 s, runs in `go test ./...` | a few minutes |
| Behaviour | asserts thresholds | asserts thresholds **and** writes every cell |

The narrow mode is what stops a recall regression from landing. The wide mode is
what the published charts are drawn from. Because they are the same code, a
threshold that CI enforces and a number printed in the README cannot disagree.

**Both modes are skipped under `-race`.** Every sweep here is single-goroutine, so
the detector has nothing to observe while costing roughly 10× — enough to push the
package past the default ten-minute timeout. Race coverage belongs to the five
`TestConcurrent*` tests, which pit readers against writers and finish in about
twenty seconds under `-race`.

## What is measured

| Sweep | Varies | Question it answers |
|---|---|---|
| `dimension` | 8 → 1536 | What does an embedding size cost, in recall and in latency? |
| `scale` | 500 → 20,000 vectors | Does search stay sub-linear as the corpus grows? |
| `ef` | 10 → 512 | The per-query knob: what does recall cost in latency? |
| `M` | 4 → 48 | The structural knob, fixed at build time — what does it buy? |
| `grid` | M 8→32 x ef 16→256 | The surface, not two slices: which (M, ef) pair is not beaten on both axes? |
| `efscale` | N 1k→20k x ef 16→512 | How much wider must the search get to hold a recall target? Fits `SuggestedEf`. |
| `metric` | Cosine / Euclidean / DotProduct | Do all three metrics actually work, not just the tested one? |
| `distribution` | centered / positive / clustered | How much does the shape of the data decide the answer? |
| `tombstones`, `compacted` | 0 → 75% dead | What deferred deletion costs, and what `Compact()` returns. |

Recall is always measured against **brute-force ground truth over the raw
corpus** — never against the graph's own stored vectors, which would let a
normalization bug cancel itself out on both sides of the comparison.

## Reading the numbers honestly

- **Latency is wall clock on one machine** (Apple M4 Max). It includes cache
  effects: past roughly 4 MB of vectors the distance kernels start paying for
  memory rather than arithmetic, which is why measured growth with corpus size
  is nearer `sqrt(N)` than the `log(N)` the algorithm implies. The scale test
  asserts only that latency stays far from linear — enough to catch a regression
  to scanning, loose enough not to flake on a busy laptop.
- **Recall at a fixed `ef` falls as the corpus grows.** That is not a defect: the
  search width stays constant while the number of plausible candidates rises. It
  is the reason `ef` is an argument to `Search` rather than a build-time
  constant. Measured, holding a target needs `ef` to grow as roughly `n^0.78` —
  sub-linear, but a good deal steeper than the `log N` the hop count follows.
  `SuggestedEf` is fitted to that surface.
- **Recall varies with the corpus, not only its size.** The same configuration
  (M=16, ef=32, N=5000) measured on three different random corpora returned
  0.595, 0.646 and 0.677 — an eight-point spread. The variance is widest in the
  middle of the recall range and compresses near saturation, which is why
  `SuggestedEf`'s anchors carry margin and why single-seed measurements at
  mid-recall should not be trusted to three decimal places.
- **The M-vs-recall chart overstates the case for raising `M`.** Compared at
  equal recall on the 2-D grid, M=32 beats M=16 by about 10% latency for 6x the
  build. Comparing two 1-D charts, each taken at the other knob's default, is the
  mistake the grid exists to prevent.
- **Corpus shape moves latency, not recall — the opposite of what was expected.**
  `positive` (components in [0,1)) puts every vector in one orthant, where any two
  are already ~0.75 similar, and the prediction was that recall@10 would suffer
  from resolving a near-tie. It does not: 0.865 against `centered`'s 0.852. What
  the shape does change is speed — `clustered` data, which is what real embeddings
  look like, searches in 38 µs against 120 µs for uniform noise, because the
  greedy descent converges far sooner. The case is kept in the sweep so that
  correction stays visible instead of turning back into folklore.

## Why the plotter is hand-written

[`plot.go`](plot.go) emits SVG directly, using nothing outside the standard
library, and carries `//go:build ignore` so it is not part of the module build.
GoVecDB has no third-party dependencies and no commands; a charting library
would have been the first exception to both. Axes, gridlines and polylines are
a couple hundred lines, which is cheaper than the dependency.
